## 将来拡張ロードマップ（バックエンド化 → 認証 → DB移行）

本アプリは、最初からバックエンドありきで作るのではなく、  
**フロントエンド単体で「要件定義 → 設計 → 実装 → 改善（リファクタ）」を完結させる**ことを優先しています。

そのうえで、将来的に **業務アプリに近い構成へ段階的に拡張できる設計**を意識しています。

---

### Phase 0（現状）：フロント単体で完結

- Vite + React + TypeScript
- localStorage による永続化（ログインなし）
- 表示切替（収支 / 収入 / 支出）
- 期間指定（今月 / 他月 / 全期間）
- 日付・金額ソート、カテゴリ整理
- 月次サマリ・グラフ表示  
  ※ 会社用はグラフなしのシンプル構成
- TypeScript による型安全性
- フィルタ・期間・ソートを重視した UI / UX 設計

**ねらい**  
バックエンドに依存せず、  
「画面設計・状態管理・データ変換・永続化」をフロントだけで整理できるようにする。

---

### Phase 1：Spring Boot による CRUD API 化

- `Account` を中心とした REST API を実装
- フロントエンドは localStorage を廃止し、API通信に切り替え
- 想定エンドポイント例  
  - `GET    /accounts`
  - `POST   /accounts`
  - `PUT    /accounts/{id}`
  - `DELETE /accounts/{id}`

**ねらい**  
フロントとバックエンドの責務を分離し、  
業務アプリに近い「API設計・データ受け渡し」を意識した構成へ移行する。

---

### Phase 2：認証（ログイン）追加

- まずはシンプルなログイン機構を導入（セッション or JWT）
- ユーザー単位でデータを分離
- 「自分の家計簿だけが見える」状態を実現

**ねらい**  
単一ユーザー前提のアプリから、  
**マルチユーザーを意識した設計**へステップアップする。

---

### Phase 3：DB 移行（H2 → PostgreSQL）

- 開発環境：H2（インメモリ / ファイル）
- 本番想定：PostgreSQL
- Flyway / Liquibase によるスキーマ管理

**ねらい**  
環境差を意識した DB 設計と、  
マイグレーション管理の経験を積む。

---

### Phase 4：品質・運用の強化

- 入力バリデーションの強化
- APIエラーハンドリング、例外設計
- E2E テスト追加
- ロギング設計
- Docker 化
- GitHub Actions による CI（ビルド / テスト自動化）

**ねらい**  
「動くアプリ」から  
**運用・保守を意識したアプリ**へのレベルアップ。

---

### このロードマップの意図

フロント単体で完成度を高めたうえで、  
**次に何をどう拡張するかを説明できること**を重視しています。

- いきなり全部入りにしない
- 段階ごとに目的を持って設計を変える
- 学習・成長のプロセスを言語化できる構成

を意識して設計しています。

期間フィルタ機能
今月／過去の月／全期間を切り替えて表示でき、月の選択肢は登録済みデータから自動生成される。

表示モード切り替え
収支すべて／収入のみ／支出のみを用途に応じて切り替え可能。

ソート機能の工夫
日付・金額での並び替えに加え、収入と支出が混在しても見やすくなるよう順序を調整。

カテゴリの固定順管理
漢字カテゴリでも表示順がブレないよう、カテゴリ順を定義して全画面で共通利用。

カテゴリ別円グラフ表示
収入・支出それぞれをカテゴリ単位で可視化し、内訳を直感的に把握できる。

円グラフのインタラクション
グラフのカテゴリをクリックすると該当項目が強調表示され、金額を確認できる。

月ごとの収支推移表示
月単位で収入・支出・収支の変化を確認でき、家計の傾向を把握しやすい。

入力バリデーション
金額やメモ文字数などを制限し、不正なデータが登録されないよう対策。

データ破損に強い設計
localStorageの読み込み失敗や古いデータ形式でもアプリが落ちないよう考慮。

レスポンシブ対応レイアウト
画面サイズに応じてレイアウトを切り替え、PC・小画面どちらでも使いやすくしている。
